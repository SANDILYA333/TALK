# Feature 2 Learning Journal: Signal-Protocol End-to-End Encryption

## 1. Why E2E Encryption Exists in TALK

In a conventional client-server chat application (such as the baseline MERN architecture):
1. Alice encrypts her message to the server over TLS/HTTPS.
2. The server terminates the TLS connection, decrypting the payload into plaintext in server RAM.
3. The server inspects, processes, and persists the plaintext message in a database (e.g. MongoDB).
4. The server creates a new TLS connection to Bob and forwards the plaintext message.

### The Vulnerability of Server-Terminated Security
Under this standard model, the server is a high-value single point of failure:
- **Malicious or Rogue Server Admin**: Can inspect all active and historic conversations.
- **Database Leaks / Cloud Breach**: An attacker who dumps MongoDB records gains plaintext access to every conversation ever recorded.
- **Subpoenas / Rogue Intermediaries**: The service provider can be compelled to provide user transcripts.

**TALK's Solution**:
End-to-End Encryption (E2EE) guarantees that message contents are encrypted on Alice's physical device and can **only** be decrypted on Bob's physical device. The server acts strictly as a blind, untrusted ciphertext relay and public key registry.

```text
Alice Device (Plaintext)
        │
        ▼ (Client-Side Double Ratchet Encrypt)
Ciphertext Envelope
        │
        ▼ (TLS in transit)
Server Relay & MongoDB (Blind Ciphertext Storage)
        │
        ▼ (TLS in transit)
Ciphertext Envelope
        │
        ▼ (Client-Side Double Ratchet Decrypt)
Bob Device (Plaintext)
```

## 2. Threat Model: Capabilities & Boundaries

### What the Attacker CAN Do
- **Compromise the Backend Database**: Gain read/write access to MongoDB and all stored ciphertext records.
- **Control the Server / Intercept Network Traffic**: Drop, reorder, delay, replay, or inject arbitrary ciphertext envelopes.
- **Maliciously Modify Public Key Registry**: Attempt to substitute forged public keys or expired prekeys.
- **Temporarily Compromise a Client Device**: Gain access to RAM state at time $T$.

### What the Attacker CANNOT Do
- Decrypt historical messages transmitted prior to a device compromise (guaranteed by **Forward Secrecy**).
- Continuously decrypt future messages after an uncompromised DH ratchet step executes on the device (guaranteed by **Post-Compromise Security / Healing**).
- Forge messages from Alice without holding Alice's private identity key and ratchet state.
- Tamper with message routing, session IDs, or counter numbers without causing AEAD authentication tag verification to fail immediately.

## 3. Encryption in Transit (HTTPS) vs End-to-End Encryption (E2EE)

| Dimension | HTTPS / TLS Only | End-to-End Encryption (Signal Protocol) |
| :--- | :--- | :--- |
| **Trust Boundary** | Client $\leftrightarrow$ Server | Client $\leftrightarrow$ Client |
| **Server Visibility** | Plaintext visible in memory and DB | Complete zero-knowledge ciphertext |
| **Database Compromise Impact** | 100% conversation exposure | 0% content exposure (all ciphertext is unreadable) |
| **Key Lifespan** | Ephemeral TLS session key | Continually ratcheted per-message keys |
| **Forward Secrecy Scope** | Protects transport channel | Protects individual messages at rest and in transit |
| **Identity Authentication** | Server authenticated via X.509 cert | Device authenticated via cryptographic identity keypairs |

## 4. Complete Cryptographic Key Hierarchy

TALK establishes a strict 7-tier key hierarchy:

```text
[ Long-Term Identity ]
  ├── X25519 Identity Key (IK_dh)       ──> DH Key Agreement & Connect ID
  └── Ed25519 Signing Key (IK_sign)     ──> Authenticates Prekeys

[ Medium-Lived Prekeys ]
  └── Signed Prekey (SPK)                ──> Signed by IK_sign, rotated every 7 days

[ Ephemeral / Disposable Prekeys ]
  ├── One-Time Prekeys (OPK_1 ... OPK_n)──> Single-use X25519 keys, deleted after 1st use
  └── Ephemeral Key (EK)                ──> Freshly generated by sender for session init

[ Double Ratchet Session State ]
  ├── Master Shared Secret (SK)         ──> Output of X3DH KDF
  ├── Root Key (RK)                     ──> Advanced by Diffie-Hellman Ratchet
  ├── Sending Chain Key (CK_s)          ──> Advanced by Symmetric Ratchet on send
  ├── Receiving Chain Key (CK_r)        ──> Advanced by Symmetric Ratchet on receive
  └── Message Key (MK)                  ──> 256-bit AES-GCM key, destroyed immediately after use
```

## 5. X3DH (Extended Triple Diffie-Hellman) Protocol

X3DH solves the fundamental problem of **asynchronous session establishment**: Alice can establish an encrypted, forward-secure session with Bob even if Bob is offline.

### Protocol Steps

```text
BOB                                 SERVER REGISTRY                            ALICE
 │                                         │                                      │
 ├── Generates IK_dh, IK_sign              │                                      │
 ├── Generates SPK, signs with IK_sign     │                                      │
 ├── Generates OPK pool (OPK_1..OPK_n)     │                                      │
 └── Uploads Prekey Bundle ───────────────>│                                      │
                                           │<─── Requests Bob's Prekey Bundle ────┤
                                           │──── Returns Bob's Bundle ───────────>│
                                           │                                      ├── Verifies Sig(IK_sign_B, SPK_B)
                                           │                                      ├── Generates Ephemeral Keypair (EK_A)
                                           │                                      ├── Computes DH1 = DH(IK_dh_A, SPK_B)
                                           │                                      ├── Computes DH2 = DH(EK_A, IK_dh_B)
                                           │                                      ├── Computes DH3 = DH(EK_A, SPK_B)
                                           │                                      ├── Computes DH4 = DH(EK_A, OPK_B)
                                           │                                      ├── SK = HKDF(DH1 || DH2 || DH3 || DH4)
                                           │                                      └── Sends initial message with EK_A
```

### Why Quadruple Diffie-Hellman?
- **$DH1 = \text{X25519}(IK_{dh}^A, SPK^B)$**: Authenticates Alice to Bob and Bob to Alice (mutual authentication).
- **$DH2 = \text{X25519}(EK^A, IK_{dh}^B)$**: Guarantees forward secrecy with respect to Alice's identity key.
- **$DH3 = \text{X25519}(EK^A, SPK^B)$**: Guarantees forward secrecy with respect to both parties' prekey material.
- **$DH4 = \text{X25519}(EK^A, OPK^B)$**: Guarantees that even if Alice's ephemeral key or Bob's signed prekey were compromised in the future, this specific session remains secure because the single-use $OPK$ was deleted.

## 6. Double Ratchet State Machine

The Double Ratchet combines two distinct ratchets into a single continuous self-healing cryptographic state machine:

### 1. The Symmetric KDF Ratchet (Per-Message Step)
For every message sent or received within the current DH phase:
- $\text{MessageKey}_{i,j} = \text{HMAC-SHA-256}(\text{ChainKey}_{i,j}, \text{"TALK-DOUBLE-RATCHET-V1:MESSAGE-KEY"})$
- $\text{ChainKey}_{i,j+1} = \text{HMAC-SHA-256}(\text{ChainKey}_{i,j}, \text{"TALK-DOUBLE-RATCHET-V1:CHAIN-KDF"})$

**Forward Secrecy**: Because HMAC-SHA-256 is a one-way cryptographic function, an attacker who obtains $\text{ChainKey}_{i,j+1}$ cannot invert it to calculate $\text{ChainKey}_{i,j}$ or $\text{MessageKey}_{i,j}$.

### 2. The Asymmetric Diffie-Hellman Ratchet (Turn-Taking Step)
Whenever a party receives a message containing a new DH public key:
- A fresh DH exchange is performed: $DH_{shared} = \text{X25519}(DH_{local\_priv}, DH_{remote\_pub})$.
- The Root Key is updated via HKDF:
  $$(RootKey_{i+1}, ChainKey_{recv}) = \text{HKDF}(RootKey_i, DH_{shared}, \text{"TALK-DOUBLE-RATCHET-V1:ROOT-KDF"})$$
- The receiver generates a fresh local DH keypair and includes the public half in their next outgoing message.

**Post-Compromise Security (Healing)**: If an adversary temporarily dumps RAM and compromises $RootKey_i$, as soon as Alice and Bob exchange fresh DH keys, the adversary is locked out because the adversary does not hold the fresh private ephemeral scalar.

## 8. Alternatives Evaluated & Rejected

### Alternative 1: Static Shared Symmetric Key (Pre-Shared Key)
- *Approach*: Derive a single AES-256 key between Alice and Bob once and use it forever.
- *Why Rejected*: Zero forward secrecy. If the key is leaked, every historic message is decrypted. No post-compromise recovery.

### Alternative 2: Pure X25519 Identity without Ed25519 (Birational Conversion)
- *Approach*: Use X25519 key for signatures via ad-hoc Montgomery-to-Edwards conversion.
- *Why Rejected*: The birational mapping between Montgomery ($u$) and Edwards ($(x,y)$) coordinates loses the sign bit of $y$. Inverting this mapping introduces signature malleability and potential cross-protocol identity confusion attacks.

### Alternative 3: Server-Assisted Message Key Derivation
- *Approach*: Ask the server to coordinate ratchet counters or salts.
- *Why Rejected*: Violates the zero-trust server boundary. The server could intentionally manipulate counters to cause nonce reuse in AES-GCM.

## 9. Formal Security Analysis (Asset $\to$ Threat $\to$ Attack $\to$ Mitigation $\to$ Residual Risk)

```text
1. Asset: Long-Term Private Identity Keys (IK_dh, IK_sign)
   Threat: Impersonation & Identity Theft
   Attack: Attacker extracts private key from local browser storage or logs.
   Mitigation: Private keys never leave IndexedDB; never transmitted over network; forbidden-secret filters strictly reject accidental serialization; zero-secret structured logging.
   Residual Risk: Full OS/device compromise (root malware on client machine).

2. Asset: Message Plaintext & Attachments
   Threat: Mass Surveillance / Database Leak
   Attack: Attacker dumps MongoDB Atlas collections or eavesdrops on WebSocket packets.
   Mitigation: Server stores and routes only AES-256-GCM ciphertext envelopes authenticated with Associated Data.
   Residual Risk: Endpoint compromised while user has chat open on screen.

3. Asset: Historical Message Transcripts
   Threat: Retroactive Decryption
   Attack: Adversary records all encrypted traffic, then compromises Bob's device 6 months later.
   Mitigation: Forward Secrecy via Double Ratchet. Message keys are erased immediately after decryption; chain keys advance via one-way HMAC; OPKs are single-use.
   Residual Risk: Unencrypted local message history stored at rest (mitigated in Feature 4).

4. Asset: Message Integrity & Sender Authenticity
   Threat: Man-in-the-Middle (MITM) / Envelope Tampering
   Attack: Malicious server modifies senderDeviceId or swaps ciphertext payload.
   Mitigation: AES-256-GCM Associated Data cryptographically binds version, sessionId, senderDeviceId, recipientDeviceId, and ratchetHeader. Tampering invalidates the 128-bit authentication tag.
   Residual Risk: Initial identity key substitution if users never verify out-of-band Safety Numbers (addressed in Feature 5).

5. Asset: Prekey Authenticity
   Threat: Prekey Spoofing on Registry
   Attack: Rogue server serves an attacker-controlled Signed Prekey for Bob to intercept Alice's X3DH handshake.
   Mitigation: Bob signs SPK with his Ed25519 identity key. Alice verifies the signature against Bob's verified identity key before executing X3DH.
   Residual Risk: None, assuming Bob's identity key is authentic.
```

## 10. Failure Modes, Edge Cases & Recovery

1. **Out-of-Order Message Delivery**:
   - *Failure*: Message #5 arrives before Message #3 due to network reordering.
   - *Resolution*: Receiver detects $N_{recv} > N_{expected}$, computes skipped message keys $MK_3, MK_4$, stores them in bounded dictionary (`MAX_SKIPPED_MESSAGE_KEYS = 1000`), advances chain to 5, and decrypts Message #5. When Message #3 arrives, it is decrypted using the stored $MK_3$ and $MK_3$ is erased.
2. **One-Time Prekey Exhaustion**:
   - *Failure*: Bob receives 500 session requests while offline; all published OPKs are consumed.
   - *Resolution*: Protocol falls back to Triple-DH ($DH1, DH2, DH3$) without $DH4$. Session is still authenticated and forward-secure, but loses the additional layer of single-use OPK forward secrecy until Bob reconnects and uploads a new OPK batch.
3. **Corrupted or Tampered Ciphertext**:
   - *Failure*: Network error flips bits in ciphertext or authentication tag.
   - *Resolution*: Web Crypto `AES-GCM` decrypt rejects the payload with an explicit `OperationError`. TALK logs a structured `CryptographicError` without exposing key bytes and prompts the UI that a message failed integrity verification.

## 11. Interview Defense & Deep Technical Questions

### Q1: Why isn't HTTPS / TLS enough for a secure chat application?
> **Answer**: TLS only protects data **in transit** between the client and the server. Once packets arrive at the server, TLS is terminated and the payload is decrypted into plaintext in server RAM and written to the database. A rogue server administrator, a compromised cloud provider, a database leak, or a legal subpoena exposes all conversations. Signal-Protocol E2EE ensures that the server only ever handles encrypted blobs that cannot be decrypted without the private keys that reside exclusively on the recipient's physical device.

### Q2: Why does X3DH require both a Signed Prekey (SPK) and One-Time Prekeys (OPKs)?
> **Answer**: X3DH enables asynchronous session setup when the recipient is offline. The **Signed Prekey** guarantees that the sender is communicating with genuine prekey material authenticated by the recipient's long-term identity key. However, because the SPK is reused across multiple sessions (rotated periodically, e.g., weekly), an attacker who compromises the SPK private key in the future could potentially compromise all sessions initiated during that window. To prevent this, **One-Time Prekeys** are generated in batches and used exactly once. Once Alice initiates a session with Bob's $OPK_1$, Bob deletes $OPK_1$ from his device, guaranteeing forward secrecy even if Bob's SPK is compromised later.

### Q3: What is the difference between Forward Secrecy and Post-Compromise Security (Healing)?
> **Answer**:
> - **Forward Secrecy** looks backwards: If an attacker steals a user's device and extracts all current cryptographic keys at time $T$, they still cannot decrypt messages sent prior to $T$. This is achieved by advancing symmetric chain keys via one-way functions (HMAC) and immediately zeroizing used message keys.
> - **Post-Compromise Security (Break-in Recovery / Healing)** looks forward: If an attacker compromises device keys at time $T$, but the user continues communicating, the protocol automatically "heals" as soon as a new asymmetric Diffie-Hellman ratchet exchange occurs. Because the fresh DH step introduces brand-new ephemeral entropy that the attacker does not possess, the attacker loses the ability to decrypt future messages.

### Q4: Why can't we use X25519 directly to sign prekeys?
> **Answer**: X25519 is an Elliptic Curve Diffie-Hellman primitive defined over Montgomery curves (RFC 7748) designed specifically for scalar multiplication ($u$-coordinate only). It does not natively produce digital signatures. Ed25519 is a digital signature scheme defined over Twisted Edwards curves (RFC 8032) using complete $(x,y)$ coordinates. While Curve25519 and Ed25519 are birationally equivalent, converting between them without transmitting sign bits introduces signature malleability and vulnerabilities. TALK adopts a clean, dual-key architecture ($X25519$ for DH and $Ed25519$ for signatures) to guarantee primitive separation and eliminate cross-protocol attacks.
